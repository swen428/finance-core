# Managed capture and local receipt publication (v1)

The managed capture entry receives text or a receipt image already obtained by the trusted Host and published through the Bridge's fixed local handoff. Core does not download a Telegram file. The trusted caller binds the original source identity, account, conversation and actor; existing canonical intake keys and frozen Telegram evidence govern replay. Request fields are not independent Telegram authentication.

Every managed local phase uses the remaining enclosing command deadline, including publication owner-lock waits; it does not restart a full publication timeout. Expired phases refuse and still perform actual close. Managed capture write phases cap SQLite busy waits at the smaller of the existing five seconds and the enclosing remainder. File synchronization and close retain cooperative checks and uncertain-close containment; a deadline is not proof that an uncertain resource has closed. Each local database phase owns a registered short managed session and keeps the profile shared gate until rollback and actual close. Text capture reuses existing interaction authority without recursively acquiring a gate. The receipt path reads only bounded fixed local handoff roles, validates image identity/hash and original caption, publishes immutable original bytes, and commits the existing attachment evidence and capture job. Filesystem publication and database commit are separate durable phases; this is not a new all-or-nothing transaction.

If publication succeeds before the database phase is interrupted, the immutable published orphan and original handoff remain evidence. Replay verifies the same source/hash/caption before reuse. After a completed capture and lawful handoff reclaim, the persisted original attachment evidence supplies the replay identity. Inconsistent, missing or conflicting evidence must refuse without replacing the canonical original. No arbitrary path or caller-owned connection authorizes a managed write.

The connection-taking generic Telegram acquisition API and old manual receipt/OCR runner are not managed entries. They must reject the managed layout before metadata/download, engine construction or extraction, while ordinary temporary-staging behavior remains separate. Their refusal does not remove the actual Host → Bridge local-handoff → Core publication owner.

S3-A does not perform OCR or providers and does not admit propose/process_capture_job or processing recovery branches. S3-B separately owns the prepare/close → external OCR wait → fresh fenced commit boundary and receipt proposal consumers. Later Bridge/Host integration owns authenticated ingress, publication/reclaim coordination and every actual runtime writer.

Synthetic evidence must cover actual managed text/image capture, lost-response replay, publication-before-DB interruption, retained orphan reuse, completed replay after handoff removal, wrong source/hash/caption before effects, concurrent unique capture, actual close/gate contention and explicit legacy pre-hook refusal. This component alone does not certify installed callers, full attachment backup completeness, cut, restore, or C01–C10.
